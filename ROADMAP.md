# ROADMAP — Call Calendar (AI version)

План развития проекта. Каждый пункт — кандидат в issue для работы агента
(issue → triage → PR → ревью), см. задачи проекта в [README](./README.md).

## Отправная точка

Код перенесён «как есть» из
[fullstack-javascript-project-386](https://github.com/kirillchistov/fullstack-javascript-project-386)
(23.07.2026). Состояние проверено запуском:

- `npm run spec:build` — TypeSpec-контракт компилируется, `docs/api/openapi.yaml` генерируется;
- `cd backend && npm test` — 10/10 тестов бизнес-правил;
- `cd frontend && npm run lint && npm run build` — линт и сборка проходят;
- `cd e2e && npm test` — 5/5 сценариев Playwright.

Текущий MVP: **один владелец** календаря (создаётся при старте), гость бронирует
30-минутный слот без регистрации, cookie-сессия владельца, in-memory-хранилище,
таймзоны через dayjs, контрактная валидация (AJV по `openapi.yaml`), демо-режим
для GitHub Pages, деплой на Render (Docker).

## Продуктовое направление

Развиваем сервис в **платформу записи к предпринимателям-экспертам**: на смену
одному владельцу приходят много экспертов с **доменной специализацией**
(маркетинг, финансы, право, IT, HR и т. д.). Гость находит эксперта по домену
и записывается на консультацию; эксперт управляет своим расписанием, типами
консультаций и профилем.

Все изменения — через Design First (AGENTS.md): сначала контракт в `spec/`,
затем `spec:build`, типы клиента и реализация.

## Этап 1. Фундамент мультиэкспертности

Самое крупное изменение контракта — переход от одного владельца к многим.

- [ ] **feat(spec): модель Expert и регистрация экспертов**
  `Owner` → `Expert` (id, slug, имя, email, описание, таймзона);
  регистрация/вход эксперта (email + пароль, bcrypt вместо фиксированных
  учётных данных); сессии остаются cookie-based.
- [ ] **feat(spec+backend): доступность и слоты в разрезе эксперта**
  `GET /api/experts/{slug}/slots`, availability на эксперта;
  бронирование привязывается к эксперту; правило «нельзя занять занятый слот»
  действует в рамках календаря эксперта.
- [ ] **feat(backend): персистентное хранилище**
  In-memory `Map` теряет данные при рестарте и не масштабируется на многих
  экспертов — перейти на SQLite (better-sqlite3) с миграцией структуры store.
- [ ] **feat(frontend): публичная страница эксперта `/e/{slug}`**
  Профиль + календарь слотов + форма бронирования (текущий гостевой флоу,
  но в разрезе эксперта).
- [ ] **test: обновить тесты бэкенда и e2e под мультиэкспертность**
  Изоляция данных экспертов: расписание и брони одного не влияют на другого.

## Этап 2. Доменная специализация и каталог

Ключевая ценность для гостя — найти эксперта в нужной области.

- [ ] **feat(spec): справочник доменов специализации**
  Модель `Domain` (slug, название, описание): маркетинг, финансы, право,
  IT-консалтинг, HR и т. д.; эксперт указывает 1–3 домена в профиле.
- [ ] **feat(frontend+backend): каталог экспертов с фильтром по домену**
  `GET /api/experts?domain=...` + главная страница со списком экспертов,
  фильтром по доменам и поиском по имени/описанию.
- [ ] **feat: типы консультаций на эксперта**
  Развить существующий `EventType`: у каждого эксперта свои типы
  («Вводный звонок 30 мин», «Разбор 60 мин»), длительность влияет на
  нарезку слотов (сейчас жёстко 30 минут), опционально — цена.
- [ ] **feat(frontend): выбор таймзоны гостя** при просмотре слотов
  (сейчас слоты показываются в таймзоне браузера без явного выбора).

## Этап 3. Ценные фичи для экспертов и гостей

- [ ] **feat: отмена и перенос брони гостем по секретной ссылке**
  Токен отмены в подтверждении брони; отмена освобождает слот, перенос —
  атомарная замена слота.
- [ ] **feat: email-уведомления** о создании/отмене брони эксперту и гостю
  (в dev — логгер/заглушка, интерфейс для подключения провайдера).
- [ ] **feat: защита от двойного бронирования на границе гонки**
  Сейчас проверка «слот свободен» и запись неатомарны — при SQLite закрыть
  транзакцией + уникальным индексом (expertId, startsAt).
- [ ] **feat: буферы и ограничения записи**
  Минимальный интервал до начала (нельзя бронировать за 5 минут), буфер
  между встречами, лимит броней в день — настройки эксперта.
- [ ] **feat: статистика для эксперта** — сводка в кабинете: брони за
  неделю/месяц, популярные типы консультаций, доля отмен.
- [ ] **feat: демо-режим для новых сущностей** — поддержать экспертов и
  домены в браузерной эмуляции API (GitHub Pages).

## Порядок работы

1. Этап 0 — короткий: привести обвязку в соответствие с этим репозиторием
   и подключить агента.
2. Этап 1 — последовательно, начиная с контракта (`spec/`): мультиэкспертность
   ломает API, поэтому сначала фиксируем его в TypeSpec, потом реализация.
3. Этапы 2–3 — независимые фичи, хорошо режутся на issues для агента.
4. Этап 4 идёт параллельно: процессные задачи отрабатываются на реальных
   фичах из этапов 1–3.

Правила коммитов и проверки перед коммитом — в [AGENTS.md](./AGENTS.md).
